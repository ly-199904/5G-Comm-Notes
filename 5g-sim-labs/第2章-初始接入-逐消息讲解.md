# 第 2 章 · 初始接入 —— 逐消息深度讲解

> 把手机从"开机"到"驻网 + 接入 RRC_CONNECTED"的每一条信号/信令拆开讲：
> 谁发、谁收、走什么信道、携带什么字段、为什么这么设计。
> 主线口诀：**搜小区 → 读广播 → 抢接入 → 建 RRC → 去注册**。

---

## 0. 先把"信道地图"摆出来

初始接入要用到的所有信号/消息，都落在下面这张三层信道映射上。后面每讲一条消息，你都能在这张表里定位它：

| 逻辑信道 | 传输信道 | 物理信道/信号 | 跑的内容 |
|---------|---------|--------------|---------|
| — | — | **PSS / SSS** | 同步信号（找时间、解 PCI）|
| BCCH | BCH | **PBCH**（+DMRS）| MIB |
| BCCH | DL-SCH | **PDCCH**（+DMRS）| SIB1/SI 的调度信息（DCI）|
| BCCH | DL-SCH | **PDSCH**（+DMRS/PT-RS）| SIB1、SI 的实际内容 |
| — | RACH | **PRACH** | 随机接入 Preamble（上行）|
| CCCH/DCCH | DL-SCH/UL-SCH | PDCCH/PDSCH/PUSCH | RRC 信令（MSG3/MSG4 等）|

一个直觉：**PSS/SSS/PBCH 是"广播喇叭"**，基站不停地往外喊，手机被动地听；**PRACH 是手机第一次"举手发言"**；从 MSG3 开始才有真正的双向 RRC 对话。

## 2.1 小区搜索与选择

这一阶段全是**下行广播信号**，手机只听不发。目标三件事：**对上时间、对上频率、解出小区身份（PCI）**。

### 信号①：PSS（主同步信号）

* **方向**：gNB → UE（广播）
* **物理信道**：直接在 SSB（SS/PBCH Block）里
* **作用**：手机扫频时第一个抓到的东西。PSS 让手机拿到**符号级/半帧级的粗定时**，并解出 **N_ID²（0/1/2 三选一）**。
* **怎么找**：手机不是全频段瞎扫，而是按协议规定的**同步栅格（Synchronization Raster / GSCN）**只在特定频点上找，省时省电。
* **底层直觉**：PSS 是一段已知的序列（m 序列），手机拿本地副本去和收到的信号做**滑动相关**，相关峰出现的位置就是定时点，峰对应的序列就解出 N_ID²。

> 对应你项目里的 **Stage 1（SSB 广播）+ Stage 2（PSS 检测）**。

### 信号②：SSS（辅同步信号）

* **方向**：gNB → UE（广播）
* **作用**：在 PSS 基础上解出 **N_ID¹（0~335）**。
* **PCI 合成**：拿到两个分量后，`PCI = 3 × N_ID¹ + N_ID²`，一共 1008 个可能值。**至此手机知道了"这个小区叫什么"。**
* **底层直觉**：SSS 由两个 m 序列相乘构成，BPSK 相乘等价于比特异或（硬件廉价）；不同 PCI 之间互相关很低（≈ −1/127，是"低互相关"不是严格正交），所以能盲检区分。

> 对应你项目里的 **Stage 3（SSS 检测 + PCI 合成）**。

### 信号③：PBCH（承载 MIB）

* **方向**：gNB → UE（广播）
* **传输信道**：BCH；**逻辑信道**：BCCH
* **作用**：手机解 PBCH 拿到 **MIB**，同时拿到 **SS/PBCH block index（波束序号）** 和定时信息，以及"去哪找 SIB1"的指引。
* **编码**：PBCH 用 **Polar 码**，还有两层解扰（夹住 Polar）和 DMRS 信道估计。
* **底层直觉**：PBCH 的 DMRS"一身二用"——既用于盲检 SSB index，又用于信道估计做相干解调。

> 对应你项目里的 **Stage 4（PBCH 译码 & MIB）**。

### 信号④：SIB1（这一阶段的终点）

* **方向**：gNB → UE（广播，周期性）
* **物理信道**：PDSCH（由 PDCCH 用 SI-RNTI 调度），**逻辑信道** BCCH
* **作用**：拿到上行初始 BWP、初始 BWP 内的信道配置、TDD 半帧配比等接入必需信息，以及"去哪找其他广播 OSI"的搜索空间。
* **找它要先做的事**：MIB 里的 `pdcch-ConfigSIB1` 告诉手机 **CORESET#0** 的时频位置（高 4 位）和监听周期（低 4 位）→ 手机在 CORESET#0 上盲检 PDCCH → 解出 **DCI 1_0** → 按 DCI 调度去 PDSCH 读 SIB1。

> 对应你项目里的 **Stage 5（CORESET#0 盲检）+ Stage 6（SIB1 解析）**。读完 SIB1，严格意义的**「驻网（camping）」就完成了**。

**小区搜索完整流程图**（书里图 2-1）：
`发送同步信号@gNB → 开机搜索小区@UE（得下行时钟同步和小区ID）→ 广播MIB@gNB → 接收解析PBCH@UE（得定时信息和SSB index、SIB1时频信息）→ 广播SIB1@gNB → 接收SIB1@UE（得基本接入信息、OSI发送方式）→ 广播OSI@gNB → 接收OSI@UE（得移动性信息）`

## 2.2 系统消息广播

系统消息让手机拿到 **AS 层**（公共信道、定时器、小区选择/重选、邻区信息）和 **NAS 层**（运营商信息）的基础信息，决定手机在小区里怎么驻留、重选、发起呼叫。

### 消息逐条：MIB（Master Information Block）

* **方向**：gNB → UE；**信道**：PBCH
* **作用**：给手机接入网络的**最必需**信息，特别是"怎么找到 SIB1"。

| 字段 | 类型 | 含义 |
|------|------|------|
| `systemFrameNumber` | BIT STRING(6) | 系统帧号**高 6 位**（SFN 共 10 位，低 4 位直接编进 PBCH payload）|
| `subCarrierSpacingCommon` | ENUM{scs15or60, scs30or120} | RMSI/MSG2/MSG4 用的子载波间隔；低频只能 15k/30k，高频只能 60k/120k |
| `ssb-SubcarrierOffset` | INTEGER(0..15) | 即 **k_SSB**，SSB 相对 CRB（公共资源块）的频域偏移 |
| `dmrs-TypeA-Position` | ENUM{pos2, pos3} | PDSCH DMRS 的符号位置 |
| `pdcch-ConfigSIB1` | INTEGER(0..255) | **关键**：高 4 位 = RMSI 的 CORESET 时频位置（查表 38.213 Table 13-1~13-10），低 4 位 = 监听周期（查表 13-11~13-14）；间接给出初始 BWP 信息 |
| `cellBarred` | ENUM{barred, notBarred} | 小区是否禁止用户驻留 |
| `intraFreqReselection` | ENUM{allowed, notAllowed} | 被 BAR 后是否允许重选到同频邻区 |

> `cellBarred` 的填法在不同场景（激活/高优先级闭塞/中低优先级闭塞/解闭塞/NG-C 故障/NG-C 恢复）和不同组网（NSA/SA/NSA&SA）下不同，书里给了对照表。

### 消息逐条：SIB1（System Information Block 1，也叫 RMSI）

* **方向**：gNB → UE；**信道**：PDSCH（PDCCH 用 SI-RNTI 调度）
* **作用**：内容比 MIB 丰富得多，是"接入说明书"。关键信元：

| 字段 | 含义 |
|------|------|
| `cellSelectionInfo` → `q-RxLevMin` | 小区选择信息，**驻留判据（S 准则）的死亡线** |
| `cellAccessRelatedInfo` | PLMN 列表、`trackingAreaCode`（带 = SA 组网；不带 = 只支持 EN-DC）、`ranac`、`cellIdentity`、`cellReservedForOperatorUse` |
| `si-SchedulingInfo` | 每条 SI 怎么调度：`si-BroadcastStatus`(broadcasting/notBroadcasting)、`si-Periodicity`、`sib-MappingInfo`、`si-WindowLength` |
| `servingCellConfigCommon` | 上下行公共参数、初始 BWP、TA、`ssb-PeriodicityServingCell`、`ss-PBCH-BlockPower`(−60..50) 等 |
| `uac-BarringInfo` | 统一接入控制（UAC），决定这次接入放不放行 |
| `ue-TimersAndConstants` | 含 T300 等定时器（默认值在此广播）|

**SI 调度小公式**（怎么算出某条 SI 在空口什么时候出现）：
* SI 窗口落在哪个无线帧：`SFN mod T = FLOOR(x/N)`，其中 `x = (n-1) × w`（n 是该 SI 在 schedulingInfoList 里的入口编号，w 是窗口长度）
* 窗口起始 slot：`a = x mod N`（N 是一个无线帧里的 slot 数，T 是该 SI 的周期）

**UAC 接入控制流程**：手机按接入类别查 `uac-BarringForAccessIdentity` → 至少一个接入 ID 对应 bit 为 0？→ 是则放行；否则生成随机数 R1(0~1) → R1 < `uac-BarringFactor`？→ 是则放行；否则生成 R2 → 起定时器 T390，时长 `(0.7 + 0.6×R2) × uac-BarringTime` → 超时后重试。**SIB1 里没 UAC 信息 = 接入不受控，所有业务都能发起。**

### 消息逐条：SI / OSI（其他系统信息）

* **方向**：gNB → UE；**信道**：PDSCH（DL-SCH）
* **内容**：SIB2/3/4（小区重选）、SIB5（异系统重选 E-UTRA）、SIB6（ETWS 主通知）、SIB7（ETWS 副通知）、SIB8（CMAS）、SIB9（GPS 时间和 UTC）。
* **封装**：OSI 被封成 **SI 消息**，在对应 **SI 窗口**内下发，由 PDCCH（SI-RNTI）调度 PDSCH（SI-Message）。

### 按需点播：ODOSI 的请求消息（MSG1 / MSG3）

有些 OSI 平时不广播（notBroadcasting），手机需要时主动"点播"。**先必须解 SIB1** 拿到该 OSI 的 `si-BroadcastStatus`：若是 broadcasting 就直接在 SI 窗口收；否则发起 ODOSI 订阅。两种请求方式：

* **MSG1 方式**：SIB1 里**配了**专用 PRACH 资源时用。`UE → MSG1 请求 OSI` → `gNB → MSG2 确认`（避免反复发）→ 立即广播被请求的 ODOSI，持续 2 个 SI-Period，到对应 BCCH MP 边界结束。适用于 PRACH 资源充足的场景。
* **MSG3 方式**：SIB1 里**没配**专用 PRACH 资源时用。`UE → MSG3 请求 OSI` → `gNB → MSG4 确认` → 同样广播 2 个 SI-Period。gNB 不分配专用 PRACH，适用于 PRACH 资源紧张的场景。

> 注意：连接态 UE 不需要 OSI，ODOSI 只涉及空闲态/非活动态 UE；该功能从 20A 版本起支持。

### 系统消息更新（什么时候要重读）

读一次就够了，**只有满足以下任一条件才重读**：①收到寻呼指示系统消息变化；②收到寻呼指示有 ETWS/CMAS；③距上次正确读取满 3 小时。

更新限定在 **BCCH 修改周期**内进行，边界由 `SFN mod m = 0` 定义。
`BCCH 修改周期(m 个无线帧) = modificationPeriodCoeff × defaultPagingCycle`，两者都在 SIB1 广播（modificationPeriodCoeff 固定为 2 不可配）。除 SIB6/7/8 外，基站靠改 SIB1 里的 **valueTag** 告诉手机"内容变了"。

## 2.3 随机接入（RA）—— 四步握手逐条拆

**为什么需要 RA**：下行同步靠广播（基站发、手机收）就行；**上行同步必须靠 RA**，因为基站根本不知道某个手机的存在和距离。RA 干两件核心事：①建立**上行同步（TA，定时提前量）**；②基站给手机**分配上行资源（UL_GRANT）**。

两种 RA：
* **竞争式（CBRA）**：手机自己从 SIB1 广播的池子挑 Preamble，可能撞车，需竞争解决。空闲/非活动态做初始接入**只能用它**（此刻网络还不认识手机）。
* **非竞争式（NCBRA/CFRA）**：基站预分专用 Preamble，不撞车、流程短（只有 MSG1+MSG2）。前提是已有 RRC 连接。

下面逐条拆**竞争式四步握手**（这是初始接入的核心，必须背）：

### MSG1：PRACH Preamble（手机的第一次"举手"）

* **方向**：UE → gNB；**物理信道**：PRACH（上行）
* **携带**：一个 Preamble（前导码）+ 隐含的 **RA-RNTI**（由 Preamble 所在的时频位置算出来，保证帧内全局唯一）+ L2/L3 消息大小指示。
* **要点**：
  - 此刻手机**没有 TA**，靠 PRACH 格式里超长的 **CP（循环前缀）和 GT（保护间隔）"吞下"未知的往返时延**盲发——这是 PRACH 最核心的物理思想。
  - Preamble 由手机随机选，**可能和别的手机撞车** → 这就是"竞争"的根源。
  - **RAR 窗口在 MSG1 发完后（≥1 个符号处的第一个 PDCCH 时机）开始计时**，不是发完瞬间。
* **底层直觉**：Preamble 是 ZC 序列，**恒包络**（相位按二次曲线爬升），自相关尖峰好检测。开环功控：`P_PRACH = preambleRecvTargetPower + 路损`。

> 对应你项目里的 **Stage 7（PRACH 随机接入）**的 Preamble 生成 + Msg1 发射。

### MSG2：Random Access Response（RAR，基站的回应）

* **方向**：gNB → UE；**物理信道**：PDCCH（用 RA-RNTI 加扰）+ PDSCH
* **携带三件套**：**Timing Advance（TA）**、**TC-RNTI（临时身份）**、**UL grant（上行授权，给 MSG3 用）**。
* **要点**：
  - 基站先发 `DCI format 1_0 with RA-RNTI` 调度 RAR 的资源（这一步复用了 CORESET#0 那套机器）。
  - RAR 里靠 **RAPID** 匹配回应的是哪个 Preamble。
  - **RAR 落在窗口中段而非第 0 时机，是 gNB 实打实的处理时延**（FFT/相关峰搜索/组 RAR），不是那 1 个符号。
  - 拥塞时 MAC 头里可塞 **退避指示 BI**，让手机随机退避防雪崩。
* **TA 的意义**：手机拿到 TA 后，把上行发送提前 N_TA × Tc，抵消传播时延，实现上行同步。TA 还能反推小区半径/距离。

> 对应你项目里的 **Stage 7** 的 RAR + TA 对齐。

### MSG3：携带 UEID（手机报上"身份"）

* **方向**：UE → gNB；**物理信道**：PUSCH（用 MSG2 给的 UL grant 发）
* **携带**：手机的身份标识（UEID）。在 RRC 建立场景里，**MSG3 就是 `RRCSetupRequest`**。
* **要点**：
  - 发完 MSG3，**竞争解决定时器（CR Timer）开始计时**。
  - 因为多个撞车的手机可能用同一个 Preamble、收到同一个 RAR、发出各自的 MSG3，所以必须靠下一步裁决谁赢。

### MSG4：竞争解决（基站宣布"谁赢了"）

* **方向**：gNB → UE；**物理信道**：PDCCH（用 TC-RNTI 加扰）+ PDSCH
* **作用**：基站做**竞争解决**——回显（echo）赢家 MSG3 里的身份。
* **判决**：
  - 手机收到 MSG4，比对回显的身份是不是自己的：**是 → 竞争成功**（绿）；**否 → 失败，退避重来**（红）。
  - 竞争解决用 **UE Contention Resolution Identity MAC CE**（回显前 48 bit）。
* **要点**：MSG4 仍用 **TC-RNTI** 加扰 PDCCH（竞争还没完全裁完）；赢家后续 **TC-RNTI 升格为 C-RNTI**（值不变）。

> 对应你项目里的 **Stage 8（RRC 建立）**的 Msg4 竞争解决。

**竞争式 RA 消息总结**（书里原话的中文化）：
1. `UE → NW`：PRACH Preamble（RA-RNTI、L2/L3 消息大小指示）
2. `UE ← NW`：Random Access Response（TA、TC-RNTI、UL grant）
3. `UE → NW`：L2/L3 消息（即 MSG3）
4. `UE ← NW`：竞争解决消息（MSG4）

**非竞争式 RA**（对照）：
1. `UE ← NW`：RACH Preamble（PRACH）Assignment —— 基站先指定专用前导
2. `UE → NW`：RACH Preamble（RA-RNTI、消息大小指示）
3. `UE ← NW`：Random Access Response（TA、**C-RNTI**、UL grant）

注意非竞争式直接给 **C-RNTI**（不是 TC-RNTI），且没有 MSG3/MSG4，因为身份是预先指定的、不用裁决。

## 2.4 RRC 连接建立 —— SRB1 的诞生

**本质**：RRC 连接建立 = 建立 **SRB1（信令承载 1）** 的过程。前两步直接复用随机接入的 MSG1/MSG2，所以真正"新"的是 MSG3/MSG4 这两条 RRC 消息。

### 五步流程

1. `UE → NW`：发起竞争式随机接入（= RA MSG1）
2. `UE ← NW`：gNB 回 MSG2（RAR）
3. `UE → NW`：**RRCSetupRequest**（= RA Msg3，走 SRB0/CCCH）
4. `UE ← NW`：gNB 分配并建立 SRB1，回 **RRCSetup**（= RA Msg4，走 SRB0/CCCH）
5. `UE → NW`：**RRCSetupComplete**（走新建的 SRB1/DCCH，捎带 NAS 消息）

完成后，gNB 和 UE 双方各自建立 SRB1 的 PDCP/RLC、MAC、L1 对等协议实体。

### 消息逐条：RRCSetupRequest

* **方向**：UE → gNB；**信道**：UL_CCCH，承载在 SRB0
* **作用**：空闲态手机要做业务时，发起建立 RRC 连接的请求。

| 字段 | 类型 | 含义 |
|------|------|------|
| `ue-Identity` | InitialUE-Identity | UE ID |
| `establishmentCause` | EstablishmentCause | RRC 建立原因 |

`ue-Identity` 是个 **CHOICE**：
```
InitialUE-Identity ::= CHOICE {
    ng-5G-S-TMSI-Part1   BIT STRING (SIZE 39),
    randomValue          BIT STRING (SIZE 39)
}
```
注册过就用网络分配的 **5G-S-TMSI**；高层没给标识，就在 **0 ~ 2³⁹-1** 之间随机选一个当临时标识（这又是一个"鸡生蛋"——还没身份只能随机造一个，所以可能撞车）。

`establishmentCause`（接入原因 → 典型场景）：
* `emergency` 紧急呼叫
* `highPriorityAccess` SIM 接入等级 AC 11~15 的用户初始入网
* `mt-Access` 被叫响应寻呼
* `mo-Signalling` 入网、TAU
* `mo-VoiceCall` VoNR 语音
* `mo-VideoCall` 视频电话
* `mo-SMS` 短信
* `mps-PriorityAccess` / `mcs-PriorityAccess`（待研究）

### 消息逐条：RRCSetup

* **方向**：gNB → UE；**信道**：DL_CCCH，承载在 SRB0
* **作用**：建立 SRB1（建立的 SRB1 是 **AM 模式**）。

| 字段 | 含义 |
|------|------|
| `radioBearerConfig` | 无线承载参数配置（含 `srb-ToAddModList`、`srb-Identity`、`pdcp-Config`）|
| `masterCellGroup` | OCTET STRING，含 CellGroupConfig |
| → `rlc-BearerToAddModList` | SRB 逻辑信道 + RLC 配置 |
| → `mac-CellGroupConfig` | 传输信道配置：SR、DRX、BSR、TAG、PHR 等 |
| → `physicalCellGroupConfig` | 物理信道配置：各种 RNTI、PDSCH HARQ-ACK 码本等 |

> `drb-ToAddModList` 等字段虽然存在，但 **RRC 建立流程不涉及 DRB**（数据承载留给后面的会话管理）。

### 消息逐条：RRCSetupComplete

* **方向**：UE → gNB；**信道**：UL_DCCH，承载在**刚建好的 SRB1**
* **作用**：宣告 RRC 连接建立完成，并**捎带 NAS 消息**（gNB 透传给核心网）。

| 字段 | 含义 |
|------|------|
| `selectedPLMN-Identity` | 从 SIB1 广播的 PLMN 列表里选中的合适 PLMN |
| `registeredAMF` | UE 推荐的注册 AMF（首次开机不带，由 gNB 在选中 PLMN 内选 AMF）|
| `guami-Type` / `s-NSSAI-List` | GUAMI 类型 / UE 支持的切片列表 |
| `dedicatedNAS-Message` | **UE 初始直传信息，gNB 透传给 AMF**（注册请求就在这里）|
| `ng-5G-S-TMSI-Value` | 5G-S-TMSI |

> 这条消息是**第 2 章和第 3 章/第 7 章的桥梁**：它一发出去，就触发了核心网的初始上下文建立和 NAS 注册流程。

### 异常分支①：RRCReject

* **方向**：gNB → UE；**信道**：CCCH，承载在 SRB0
* **作用**：资源不够时拒绝本次请求，携带 `waitTime`。
```
RRCReject-IEs ::= SEQUENCE {
    waitTime               RejectWaitTime,
    lateNonCriticalExtension  OCTET STRING,
    nonCriticalExtension      SEQUENCE{}
}
```
* **手机处理**：收到后停 **T300**、复位 MAC 并释放 MAC 配置、通知上层建立失败；再按 `waitTime` 起 **T302**，运行期间禁止发新请求，超时后才能发。

### 异常分支②：RRC 重发处理（两个关键定时器）

* **竞争解决定时器（ra-ContentionResolutionTimer）**：
  - 时长 gNB 经 SIB1 广播，**64ms，不可配**。
  - 启动：UE 初始传递或重传 RRCSetupRequest 后；
  - 停止：收到 RRCSetupRequest 的 HARQ ACK，或收到 RRCSetup/RRCReject；
  - 超时处理：重新做随机接入。
  - gNB 侧会做"重发检测"：收到同一用户从同一小区重发的 RRCSetupRequest 后，重发 RRCSetup，**初传不算失败**。

* **T300**：
  - 时长 gNB 经 SIB1 广播，**默认 2000ms**，可配（取值 ms100~ms2000）。
  - 启动：UE 初始传递 RRCSetupRequest 后；
  - 停止：收到 RRCSetup/RRCReject，或 UE 发起重选，或上层连接中断；
  - 超时处理：结束本次 RRC 接入，可重新发起新的 RRC 连接请求。
  - 关系：T300 启动期间没收到 RRCSetup，会在竞争解决定时器超时后反复重发**同样内容**的 RRCSetupRequest，直到 T300 超时；T300 超时后发一个**新的** RRCSetupRequest。

## 2.5 注册流程

第 2 章在这里只指路：注册属于 **NAS 流程**，详见第 7 章。但要记住衔接点——`RRCSetupComplete` 捎带的 NAS 消息（Registration request）一到核心网，就开启了"鉴权 → NAS 安全 → 注册接受"的高层对话。

 │  ┌─ 随机接入（第一次举手 + 四步握手）──────────────┐
 ├─ MSG1 (PRACH Preamble, RA-RNTI)        UE→gNB
